# Tier 3 startup diagnostics

This diagnostic path is for a measured VPSBG boot that does not expose port
8091 after `unified_server` begins loading the two Direct ORAM databases. It is
designed to distinguish a slow operation, a userspace panic/abort, an OOM or
kernel I/O stall, and a runner/readiness failure without reading or rebuilding
any database, proof, or ORAM payload for diagnostic purposes.

## Safety boundary

- The Rust recorder writes only fixed stage names, sequence numbers, elapsed
  times, DB IDs, ORAM levels, and store kinds. It never writes paths, keys,
  roots, proofs, query data, command lines, environment variables, or file
  descriptor contents.
- The watchdog is read-only with respect to `unified_server`. It samples a
  bounded set of `/proc` and filtered kernel fields at 30, 60, and 180 seconds.
  It sends no request or signal and never opens an ORAM file.
- Diagnostic writes use file-scoped `fdatasync`/`fsync`. They do not use
  BusyBox `sync -f`, whose `syncfs` behavior would flush the filesystem that
  contains the ORAM images and perturb the startup being observed.
- No database proof, Merkle tree, checkpoint, delta, or Direct ORAM image is
  regenerated by this workflow.

## Evidence layout

The initramfs mounts the existing writable data partition and creates:

```text
/home/pir/data/.runtime/tier3/<boot-id>/
├── init-events.log
└── attempt-<n>/
    ├── runner.meta
    ├── events.log
    ├── watchdog-0030.txt
    ├── watchdog-0060.txt
    ├── watchdog-0180.txt
    ├── watchdog-ready.meta
    └── exit.meta
```

Files are mode 0600 below root-only directories. Each boot has a kernel boot
ID, and each runit restart gets a fresh monotonically increasing attempt (up
to 16 per boot). Existing attempt files are never replaced.

The volatile control plane under `/run/bpir` binds readiness to the complete
tuple:

```text
schema boot-id attempt pid process-start-ticks port
```

Cloudflared starts only when the current tuple, Rust-published ready tuple,
live process start time, canonical `unified_server` executable, and port all
agree. There is no fixed 60-second fallback and no `nc -z` probe.

## Interpreting a failed boot

After waiting at least 180 seconds, switch the VPSBG UKI setting back to
`None`, reboot the stock system, and inspect the newest boot directory:

```bash
sudo find /home/pir/data/.runtime/tier3 -maxdepth 3 -type f -print
sudo sed -n '1,240p' /home/pir/data/.runtime/tier3/<boot-id>/init-events.log
sudo sed -n '1,320p' /home/pir/data/.runtime/tier3/<boot-id>/attempt-<n>/events.log
sudo sed -n '1,320p' /home/pir/data/.runtime/tier3/<boot-id>/attempt-<n>/watchdog-0180.txt
sudo cat /home/pir/data/.runtime/tier3/<boot-id>/attempt-<n>/exit.meta
```

Use the last complete `events.log` line as the primary boundary:

| Last evidence | Meaning |
| --- | --- |
| no attempt directory | failure remained in takeover init; inspect `init-events.log` and console |
| `runner.meta`, no `events.log` | runner or Rust process setup failed before recorder creation |
| `event=begin` without matching `ok`/`error` | process stopped or remained inside that exact stage |
| `event=error` | that stage returned a handled error before outer panic/exit handling |
| `direct_store_open` | `db`, `level`, and `store` identify the exact image class being opened |
| `direct_auth_domain_validate` | persisted authentication state did not bind to the expected level/store domain |
| `direct_auth_bind` | store opened, but trusted Merkle/authentication state binding failed or stalled |
| `direct_oram_restore` | files and authentication state opened; controller reconstruction is the boundary |
| `direct_reader_init` | ORAM restored; typed Direct index/chunk reader construction is the boundary |
| `listener_bind` | all database/ORAM initialization completed; socket bind is the boundary |
| `startup_complete`, then `ready_publish begin` and a live service | the ready marker itself completed publication; no log write occurs after it |

An `error` event can be advisory when the server has an explicitly degraded
fallback. In particular, `vcek_load error` means the configured VCEK chain
could not be loaded but the process continued with empty certificate fields.
The ready marker means the configured network service is running; it does not
by itself assert that runtime attestation or an operator identity passed client
verification.

In watchdog snapshots, `process_exe=unified_server` means the runner has
already executed the measured binary. `process_exe=other` means the same
PID/start-time tuple was still in its pre-exec runner; no path is persisted.
`exit.meta` records the runit exit code/signal even when Rust could not create
its recorder.

## Rollout sequence

1. Build the exact committed `unified_server`, initramfs, and UKI on the clean
   Hetzner builder. Verify the extracted initramfs and reproduce the Nix
   derivation before archiving hashes.
2. Upload the diagnostic UKI in the VPSBG portal and reboot once.
3. If the endpoint does not become ready, leave the VM alone for at least 180
   seconds so all bounded snapshots can finish. Do not issue test queries.
4. Set UKI back to `None`, reboot, and collect the persistent directory above.
5. Attribute the boundary from fixed-stage evidence before considering any
   repair or data regeneration.
